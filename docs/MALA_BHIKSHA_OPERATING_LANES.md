# Mala / Bhiksha Operating Lanes

This note keeps two different routes from collapsing into one blurry handoff.
The larger target architecture is in
[`MALA_BHIKSHA_REFACTOR_ARCHITECTURE.md`](MALA_BHIKSHA_REFACTOR_ARCHITECTURE.md).

## Lane 1: Playbook Consultant to Automation

This is the Mala 2.2 playbook-design lane.

```text
Mala playbook design
  -> chart/replay consultation
  -> reviewable playbook packet
  -> Bhiksha runtime adapter and feature-parity test
  -> trader-desk take/pass and management selection
  -> supervised shadow consultant
  -> automated execution packet only after confidence grows
```

Names:

- **Playbook packet:** a reviewable Mala artifact that describes state, cohort
  evidence, trigger/invalidation logic, management policies, and vehicle
  constraints. It may be advisory-only.
- **Bhiksha playbook adapter:** the runtime code and feature transforms Bhiksha
  needs before it can recompute the same state live.
- **Execution packet:** a playbook packet that has a matching Bhiksha adapter,
  shadow evidence, operator approval, and fail-closed runtime checks.

Default stance: playbook packets start as consultant artifacts. They do not
become automated just because the historical surface is interesting.

## Lane 2: M1-M5 Evidence to Shadow/Live

This is the older hypothesis-to-strategy promotion lane.

```text
Mala hypothesis
  -> M1-M5 gates
  -> thesis-exit optimization and provider review where relevant
  -> Mala_Evidence_v1 evidence packet
  -> active_strategy operator authorization
  -> Bhiksha active-plan compile
  -> Bhiksha shadow
  -> operator-approved live promotion
```

Names:

- **Evidence packet:** a `Mala_Evidence_v1` row generated by Mala after staged
  research gates. It is advisory until the operator authorizes it.
- **Active strategy row:** the operator authorization surface Bhiksha reads.
- **Runtime deployment:** the Bhiksha-compiled deployment that can shadow or
  trade, subject to Bhiksha capability checks and execution mode.

Default stance: passing M1-M5 does not prove runtime parity. Bhiksha must still
show that it can recompute the same features and trigger semantics live.

## Shared Rule

Mala owns research evidence and consultation logic. Bhiksha owns live feature
recomputation, option selection, execution management, and audit logging. Any
lane that crosses from Mala into Bhiksha needs an explicit feature contract,
runtime capability check, shadow evidence, and operator approval.
